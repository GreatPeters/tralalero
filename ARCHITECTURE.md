Every run records a local audit report and verifies missing-reference delta, scene hash, atlas configuration, static counts, and second-run idempotence.
- `UpgradeShopReferenceSetup` resolves the permanent-upgrade panel from the main `Upgrade_Button` UnityEvent instead of a duplicate hierarchy name, then rebuilds that reachable panel without replacing `UpgradeUI` purchase behavior. It uses the generated shoe-workshop background, one title sign, the existing global back flow, and nine data-bound parchment cards with current/next value, description, row-driven currency price bar, and a three-column layout.
- Ocean and Map 2 water optimization is stored as scene-instance overrides against generated two-triangle meshes. The shared Meshy ocean prefab remains unchanged so recovery and non-map scenes keep their source asset.
- Android texture limits and streaming mipmaps are applied only to Noryangjin Meshy textures used by the authored scenes. See `docs/noryangjin-mobile-optimization.md` for budgets, exclusions, and measured scene results.
- Build Settings keep `Noryangjin_MapTool_Mode` enabled at index `0` as the default boot scene and `Forward March Mode` enabled at index `1`; Map 2 and SR18 are deliberately excluded until their runtime timing and encounter contracts are specified. ## Forward Enemy Animation

- The six Forward enemy prefabs (`Enemy_FatMan`, `Enemy_Guard`, `Enemy_OldMan`, `Enemy_Woman`, `Enemy_YllowMan_Net`, and `Enemy_YllowMan_Sword`) each own a valid Humanoid Avatar and a character-specific `AnimatorOverrideController`. The net variant preserves the original held waffle-grid prop. The sword variant reuses the Woman boss sword mesh/material and slash animation, defaults movement animation to `run`, and uses movement speed `4` for rusher-oriented authoring.
- `Assets/JH/Model/Animatior/ForwardEnemyShared/ForwardEnemyShared.controller` is their single shared state machine. Its exact states are `idle` (default), `attack_loop`, `walk`, `run`, `die`, and `attack_once`; `attack_once` returns to `idle` after one cycle, and every assigned idle clip is imported with looping enabled.
- `EnemyScript_space` is owned only by the six Forward enemy prefabs. It is a Noryangjin encounter component, not the pooled-enemy base used by other modes: chapter progression injects runtime health, damage, and tier; one `EnemySO` supplies hit/death feedback and score; and only FatMan/Guard configure the optional held-projectile fields. The legacy `Space/EnemyType*` prefabs no longer carry this component.
- `EnemyEventController` owns event animation and facing. `EnemyScript_space` delegates a throw to `attack_once` and death to `die`; health labels still refresh only when their value changes rather than formatting text for every enemy on every frame.
- FatMan and Guard resolve their throw direction at the release frame from the release point to the current player root-collider center. The projectile local X axis and rigidbody velocity use that same direction, so rotated or moving enemy instances no longer throw sideways.
- Character clips are assigned under `ForwardEnemyShared/Overrides`. OldMan, Woman, and YllowMan reuse their attack clip in the `idle` slot because their source assets do not contain a separate idle clip. Only `walk` and `run` use the CC0 Quaternius source at `Assets/ThirdParty/Quaternius/UniversalAnimationLibrary/UAL1_Standard.fbx` (`Armature|Walk_Loop` and `Armature|Sprint_Loop`). Every earlier idle/attack/death clip and the previous `ForwardEnemy_Locomotion.anim` asset remain intact.
- Rebuild or repair the assets with `Tools/Shooter Survival/Forward Enemy/Build Shared Animator Setup`. The operation is idempotent and must not save or modify an open scene.

## Forward Enemy Events

- The six Forward enemy prefab roots carry `EnemyEventController`. Each instance selects exactly one triggered mode: repeat its attack, attack once then idle, shoot once, move to one target and then repeat its attack, or patrol between its authored start and one target while playing `attack_once` at both endpoints. Movement animation independently selects none (looping idle), walk, or run.
- The Noryangjin map tool automatically aligns a Forward enemy placed from the enemy palette to the player's travel direction at that map position. It resolves the nearest route section from the player's authored start transform and the turn spots, while preserving each section's exact initial/outgoing direction instead of using a slightly diagonal line between offset trigger centers. The placement preview uses the same result; selected and all-enemy alignment buttons repair existing placements. Copy placement deliberately preserves the source instance rotation so manual encounter overrides remain reusable. If the scene has no player route, the authored palette Y rotation is retained, and every placed enemy can still be rotated manually afterward.
- Movement modes use one external target `Transform`; the Inspector and map-tool selected-enemy card can create it with `이동 목표 만들기`, and the Scene handle edits that single point.
- `EnemyEventActivationSpot` is a rendererless player-root `BoxCollider` trigger. It serializes only linked enemies—there is no `oneShot`/`on shot` option—and disables after any linked event accepts activation. It resets for the next run.
- The map-tool palette exposes the spot as `적 발동 스팟`. Selecting it makes it the active SceneView mapping owner: enemy clicks toggle links, connection lines show the result, and `Esc` clears the spot selection. Event mode and target remain owned by each enemy.
- `EnemyEventController` delays first placement capture until its first runtime update because pooled enemies are enabled before `EnemySpawnerScript` assigns the final spawn transform. Re-enabling a scene-authored enemy preserves and restores its captured start; re-enabling an enemy while it is still parented under `EnemyPooler` deliberately requests a fresh post-spawn capture.
- Map-tool position, snap, height, and rotation edits notify an initialized `EnemyEventController`. Its cached start and route axes therefore follow `한 칸 이동`, Undo/Redo, and other authoring changes.
- `GameManager.OnTapToPlay` resets active event controllers and consumed activation spots before gameplay resumes.
- Triggered projectile delay advances only while gameplay and the time factor advance. Zero-speed movement is rejected; destroyed targets cancel to idle once. Legacy mode 3 normalizes to move-then-attack. Idle previews preserve authored rotation; movement/attacks use explicit mesh-forward correction, not the placement's idle half-turn.
- `ForwardEnemyMovementSetup.Configure` remains an internal repair API for the six default prefab components and the trigger prefab. It is not exposed in the map-production menu and does not save an open scene.

## Current Constraints
- A large portion of gameplay logic is still `MonoBehaviour`-heavy and scene-coupled.
- Pure logic extraction is limited, so most verification still needs runtime harnesses.
- Some naming and folder boundaries are inconsistent (`Obstackle`, mixed UI folders, `_space` variants).

## Agent-Oriented Architecture Rules
- Extract pure logic when a rule can be tested outside a scene.
- Keep scene-coupled logic thin where practical.
- Prefer explicit helper methods over repeated inline behavior.
- Prefer stable, named verification entry points over one-off debug edits.
- Do not hide new operational requirements in comments or chat only.
